# Supabase 안내와 보안 대비

이 문서는 Palettra Games 홈페이지가 Supabase를 어떻게 쓰는지, 어떤 위험이 있고 무엇으로 막고 있는지, 운영자가 직접 해 두어야 할 일이 무엇인지를 정리합니다. 2026년 10월 4일 실제 프로젝트를 연결하고 점검한 결과를 기준으로 썼습니다.

- 키·비밀번호·이메일 같은 실제 값은 이 문서에 적지 않습니다. 값은 `.env.local`과 Supabase 화면에만 둡니다.
- Supabase 화면의 메뉴 이름은 바뀔 수 있습니다. 찾기 어려우면 화면 위쪽 검색(`Ctrl K`)에 이름을 넣어 찾습니다.
- 요금과 한도는 `docs/EXTERNAL-SERVICES.md`(2026년 10월 1일 조사)를 봅니다.

---
## 1. Supabase가 이 홈페이지에서 하는 일

Supabase는 데이터베이스·로그인·파일 저장을 한꺼번에 제공하는 서비스입니다. 이 홈페이지에서는 아래 일을 맡습니다.

| 기능 | Supabase의 어느 부분 | 연결 전(시연 모드) | 연결 후 |
| --- | --- | --- | --- |
| 회원가입·로그인·비밀번호 재설정 | 인증(Auth) | 닉네임만 쓰는 시연 로그인 | 이메일 계정, 간편 로그인 |
| 댓글·답글·반응·신고 | 데이터베이스 | 새로고침하면 사라짐 | 저장됨 |
| 개발 뉴스·상품 등록 | 데이터베이스 | 시연 글만 표시 | 관리자가 등록한 글 표시 |
| 뉴스·상품·댓글 이미지 | 파일 저장소(Storage) | 올릴 수 없음 | 저장됨 |
| 문의 접수와 문의함 | 데이터베이스 | 검증만 하고 저장 안 함 | 저장됨 |
| 출시 알림 신청 | 데이터베이스 | 검증만 하고 저장 안 함 | 저장됨 |
| 관리자 화면 | 인증 + 데이터베이스 | 데모 화면만 | 실제 관리 |

홈페이지는 두 가지 길로 Supabase와 통신합니다.

1. **브라우저에서 바로**: 로그인, 댓글 읽기·쓰기, 반응, 신고. 방문자의 브라우저가 공개 키로 Supabase에 직접 요청합니다.
2. **홈페이지 서버를 거쳐서**: 뉴스·상품 목록, 문의 접수, 출시 알림 신청, 관리자 화면. 서버가 요청 횟수 제한과 입력 검증을 먼저 합니다.

1번 때문에 **"공개 키만 있으면 누구나 Supabase에 직접 요청을 보낼 수 있다"**는 점이 보안의 출발점입니다. 그래서 화면이 아니라 데이터베이스 자체에 "누가 무엇을 할 수 있는지"를 걸어 두었습니다(4절).

## 2. 현재 연결 상태 (2026년 10월 4일)

| 항목 | 상태 |
| --- | --- |
| 요금제 | 무료(Free) |
| 지역 | 서울(Northeast Asia) |
| 데이터베이스 설정 | 마이그레이션 아홉 개 적용(`supabase/migrations/`). 2026-10-08에 추가한 열 번째(`202610080001_account_services.sql`, 통합 계정)는 아직 적용 전 |
| 로그인 방식 | 이메일·비밀번호만 켜짐. 간편 로그인은 아직 꺼짐 |
| 이메일 확인(Confirm email) | 켜짐. 메일 발송을 연결하기 전에는 인증 메일이 오지 않아 시험할 때만 잠시 끕니다 |
| 서버 전용 비밀 키 | 홈페이지에 넣지 않음(출시 알림 확인 메일을 켤 때만 필요) |
| 자동 백업 | 없음(무료 요금제). 7절의 수동 백업 참고 |

무료 요금제의 한도는 데이터베이스 500MB, 파일 저장 1GB, 월간 활성 사용자 5만 명, 전송량 5GB입니다. **1주일 동안 사용이 없으면 프로젝트가 일시정지**되며 Supabase 화면에서 다시 켤 수 있습니다.

## 3. 키와 비밀번호 — 가장 중요한 부분

Supabase에는 성격이 다른 값이 여러 개 있습니다. 어느 것이 공개돼도 되고 어느 것이 절대 새면 안 되는지 구분하는 것이 보안의 절반입니다.

| 값 | 공개돼도 되나 | 두는 곳 | 새면 생기는 일 |
| --- | --- | --- | --- |
| 프로젝트 주소(`…supabase.co`) | 됨 | `.env.local`, 배포 환경 변수 | 없음. 원래 브라우저에 보이는 값 |
| 공개 키(Publishable, `sb_publishable_…`) | 됨 | `.env.local`, 배포 환경 변수 | 없음. 원래 브라우저에 보이는 값이며, 이 키로 할 수 있는 일은 데이터베이스 권한이 정함 |
| **비밀 키(Secret, `sb_secret_…`)** | **절대 안 됨** | `.env.local`의 `SUPABASE_SECRET_KEY`에만 | 모든 권한 규칙을 건너뛰고 전체 데이터를 읽고 지울 수 있음 |
| **데이터베이스 비밀번호** | **절대 안 됨** | 비밀번호 관리 프로그램 | 데이터베이스에 직접 접속해 전체 데이터를 읽고 지울 수 있음 |
| **Supabase 계정 로그인** | **절대 안 됨** | 본인만 | 프로젝트 전체를 조작·삭제할 수 있음 |
| **홈페이지 관리자 계정 비밀번호** | **절대 안 됨** | 본인만 | 뉴스·상품을 바꾸고 문의 내용을 읽고 댓글을 지울 수 있음 |
| 관리자 이메일(`ADMIN_EMAIL`) | 굳이 알릴 필요 없음 | `.env.local`, 배포 환경 변수 | 직접 피해는 없지만 로그인 시도의 표적이 됨 |

지켜야 할 규칙은 다음과 같습니다.

- 비밀 키·비밀번호를 **채팅, 문서, 화면 캡처, GitHub**에 올리지 않습니다. Supabase 화면을 캡처할 때 API Keys 화면이 찍히지 않게 합니다.
- 비밀 키를 `NEXT_PUBLIC_`으로 시작하는 항목에 넣지 않습니다. 그 이름의 값은 브라우저로 그대로 나갑니다.
- `.env.local`은 GitHub에 올라가지 않도록 설정되어 있습니다(`.gitignore`). 이 파일을 다른 이름으로 복사해 두지 않습니다.
- 값이 올바른 자리에 있는지는 아래 명령으로 확인합니다. 값 자체는 화면에 표시하지 않고, 비밀 키가 공개 자리에 있으면 오류로 알려 줍니다.

```powershell
# 외부 서비스 연결 점검
pnpm services:check
```

이 홈페이지는 비밀 키를 한 곳(`lib/notify/confirmation.ts`, 출시 알림 확인 메일)에서만 쓰며, 브라우저로 나가는 코드가 이 키를 불러오면 자동 검사가 실패합니다. 지금은 비밀 키를 넣지 않았으므로 **홈페이지 쪽에서 비밀 키가 샐 길은 없습니다.**

## 4. 저장하는 정보와 권한

### 4.1 표와 개인정보

| 표 | 담는 내용 | 개인정보 | 방문자(비로그인) | 로그인 회원 | 관리자 |
| --- | --- | --- | --- | --- | --- |
| `news_posts` | 개발 뉴스 | 없음 | 공개 글만 읽기 | 공개 글만 읽기 | 읽기·쓰기 |
| `products` | 상품 | 없음 | 공개 상품만 읽기 | 공개 상품만 읽기 | 읽기·쓰기 |
| `member_profiles` | 닉네임, 가입 동의 시각 | 닉네임 | 닉네임 등 공개 열만 읽기 | 본인 것만 만들고 고침 | 공개 열 읽기 |
| `news_comments` | 댓글 | 댓글 내용 | 공개 댓글만 읽기 | 본인 이름으로 쓰고 지움 | 숨김·삭제 |
| `comment_reactions` | 좋아요 등 반응 | 없음 | 읽기 | 본인 것만 | 읽기 |
| `comment_reports` | 댓글 신고 | 신고자 식별자 | 불가 | 본인이 신고, 본인 것만 읽기 | 읽기·처리 |
| `moderation_actions` | 관리 처리 기록 | 관리자 식별자 | 불가 | 불가 | 읽기·쓰기 |
| `contact_messages` | 문의 | **이메일, 문의 내용** | 넣기만 가능(읽기 불가) | 넣기만 가능 | 읽기·처리 |
| `comment_banned_words` | 댓글 금칙어 | 없음 | 불가 | 불가 | 읽기·추가·삭제 |
| `release_notifications` | 출시 알림 신청 | **이메일** | 직접 접근 불가(신청 함수만) | 직접 접근 불가 | 읽기 |
| `account_services` | 통합 계정에 연결하는 서비스 목록 | 없음 | 불가 | 읽기 | SQL Editor에서 클라이언트 식별자 입력 |
| `member_service_links` | 회원별 서비스 연결 기록(이용일, 서비스가 알려 준 요약) | 서비스 이용 사실, 서비스 안 닉네임 | 불가 | 본인 것만 읽고 지움(쓰기는 등록된 서비스의 로그인으로만) | 직접 접근 불가 |
| Supabase 인증(`auth.users`) | 계정 | **이메일, 암호화된 비밀번호** | 불가 | 본인 로그인만 | Supabase 화면에서만 |

비밀번호는 홈페이지가 저장하지 않습니다. Supabase가 암호화해 보관하며 관리자도 원래 비밀번호를 볼 수 없습니다.

### 4.2 파일 저장소

| 버킷 | 용도 | 올릴 수 있는 사람 | 제한 |
| --- | --- | --- | --- |
| `news-images` | 뉴스 대표 이미지 | 관리자 | 5MB, JPEG·PNG·WebP |
| `product-images` | 상품 이미지 | 관리자 | 5MB, JPEG·PNG·WebP |
| `comment-images` | 댓글 첨부 이미지 | 로그인 회원(본인 폴더에만) | 5MB, JPEG·PNG·WebP·GIF |

세 버킷은 "공개 버킷"입니다. **올라간 이미지는 주소를 아는 누구나 볼 수 있습니다.** 공개 화면에 보여 주기 위한 것이므로 의도한 동작이지만, 개인정보가 담긴 이미지를 올리면 안 됩니다. 파일 목록을 훑어보는 것은 막혀 있습니다.

### 4.3 이미 들어가 있는 보호 장치

- **행 단위 보안(RLS)**: 모든 표에 켜져 있습니다. 공개 키로 직접 요청해도 4.1 표의 범위 밖 일은 데이터베이스가 거부합니다.
- **열 단위 권한**: 회원 프로필에서 가입 동의 시각 같은 열은 방문자가 읽을 수 없습니다. 문의는 방문자가 분류·이메일·제목·내용 네 열만 넣을 수 있습니다.
- **관리자 판정**: 관리자 여부는 Supabase 계정의 `raw_app_meta_data`(본인이 고칠 수 없는 영역)에 있는 `role: admin`으로 정합니다. 회원이 스스로 관리자가 될 수 없습니다. 홈페이지는 여기에 더해 `ADMIN_EMAIL`과 같은 이메일인지도 확인합니다.
- **데이터베이스 쪽 댓글 제한**: 30초에 1개, 10분에 5개, 같은 내용 반복, 링크 3개 이상, 금칙어를 데이터베이스가 직접 막습니다. 화면을 거치지 않은 요청에도 적용됩니다.
- **댓글 공개 상태 보호**: 회원이 자기 댓글의 숨김·삭제 상태를 직접 바꿀 수 없습니다.
- **함수로만 여는 문**: 출시 알림 신청·확인·수신 거부, 회원 탈퇴는 정해진 함수로만 할 수 있습니다. 확인 값 발급은 비밀 키만 실행할 수 있습니다.
- **홈페이지 서버의 제한**: 문의·출시 알림은 요청자별 10분 5회 제한, 본문 크기 제한, 입력 검증, 자동 입력 방지(숨김 칸)를 거칩니다.
- **글자로만 표시**: 뉴스·댓글·문의 내용은 화면에 글자로만 넣습니다. 내용에 스크립트를 적어도 실행되지 않습니다.
- **자동 검사**: `tests/supabase-migrations.test.mjs`가 시험용 데이터베이스에 마이그레이션을 실제로 실행하고, 방문자·회원·관리자·비밀 키 역할로 바꿔 가며 위 권한을 확인합니다. `pnpm check`에 포함됩니다.

### 4.4 실제 프로젝트 점검 결과 (2026년 10월 4일)

공개 키만 가진 방문자 입장에서 "막혀 있어야 하는 일"을 실제 프로젝트에 시도했습니다.

| 시도 | 결과 |
| --- | --- |
| 뉴스·상품·댓글·프로필·신고·관리 기록·금칙어 쓰기 | 모두 거부 |
| 출시 알림 표에 직접 쓰기, 문의에 처리 상태 넣기 | 거부 |
| 문의·신고·가입 동의 시각 읽기 | 거부 |
| 탈퇴 함수, 확인 값 발급 함수, 집계 함수 실행 | 거부 |
| 뉴스·상품·댓글 이미지 올리기 | 거부 |
| 저장소 파일 목록 보기 | 빈 목록(훑어볼 수 없음) |
| 허용되지 않은 형식의 파일 올리기 | 거부 |

확인하지 못한 것은 로그인한 회원의 동작입니다(계정이 필요함). 이 부분은 시험용 데이터베이스의 자동 검사로만 확인했고, 실제 프로젝트에서는 회원가입 뒤 한 번 더 봐야 합니다.

## 5. 걱정되는 상황과 대비책

### 5.1 키나 비밀번호가 새는 경우

- **무슨 일이 생기나**: 공개 키와 프로젝트 주소는 새도 괜찮습니다. 비밀 키나 데이터베이스 비밀번호가 새면 전체 데이터를 읽고 지울 수 있습니다.
- **이미 되어 있는 것**: 비밀 키를 쓰는 곳이 한 군데뿐이고 지금은 넣지도 않았습니다. `.env.local`은 GitHub에 올라가지 않습니다. 점검 명령이 잘못된 자리의 비밀 키를 찾아냅니다.
- **직접 할 일**: 3절의 규칙을 지킵니다. 데이터베이스 비밀번호는 비밀번호 관리 프로그램에 보관합니다. 샌 것 같으면 6.1절대로 바로 교체합니다.

### 5.2 계정을 빼앗기는 경우

- **무슨 일이 생기나**: Supabase 계정을 빼앗기면 프로젝트 전체를, 홈페이지 관리자 계정을 빼앗기면 뉴스·상품·문의·댓글 관리를 조작당합니다. 실제 사고의 대부분은 권한 설정보다 이쪽에서 납니다.
- **이미 되어 있는 것**: 관리자 화면은 로그인과 관리자 역할, 이메일을 모두 확인합니다. 회원이 스스로 관리자가 될 수 없습니다.
- **직접 할 일**
  - Supabase 계정에 **2단계 인증**을 켭니다(계정 설정 → Security). GitHub로 가입했다면 GitHub에도 2단계 인증을 켭니다.
  - 관리자 계정 비밀번호는 길고, 다른 곳에서 쓰지 않는 것으로 정합니다.
  - 관리자 계정 이메일의 메일함(예: Gmail)에도 2단계 인증을 켭니다. 비밀번호 재설정 메일이 그 메일함으로 가기 때문입니다.
  - 공용 컴퓨터에서 관리자로 로그인하지 않습니다.

### 5.3 권한 설정을 실수로 푸는 경우

- **무슨 일이 생기나**: Supabase 화면에서 표의 행 단위 보안(RLS)을 끄거나 "모두 허용" 정책을 추가하면, 그 표를 누구나 읽고 쓸 수 있게 됩니다.
- **이미 되어 있는 것**: 모든 표는 마이그레이션 파일로 만들었고 자동 검사가 권한을 확인합니다.
- **직접 할 일**
  - Supabase의 Table Editor에서 **RLS를 끄지 않습니다.** "RLS disabled" 경고가 보이면 바로 다시 켭니다.
  - Supabase 화면에서 직접 새 표를 만들지 않습니다. 필요한 변경은 마이그레이션 파일로 만들어 검사를 거칩니다.
  - 가끔 **Advisors → Security Advisor**를 열어 경고가 없는지 봅니다. Supabase가 권한이 빠진 표나 위험한 설정을 찾아 줍니다.

### 5.4 스팸과 도배

- **무슨 일이 생기나**: 공개 키로 직접 요청을 보내 가짜 가입, 가짜 문의, 가짜 출시 알림 신청, 댓글 도배를 시도할 수 있습니다.
- **이미 되어 있는 것**: 댓글은 데이터베이스가 직접 제한합니다. 출시 알림은 같은 게임·같은 이메일을 한 번만 저장하고, 확인 메일로 본인 신청임을 확인한 주소에만 소식을 보냅니다. 홈페이지 서버를 거치는 문의·출시 알림은 10분 5회로 제한합니다.
- **남아 있는 약점**(8절): 문의 표는 홈페이지를 거치지 않고 직접 넣으면 횟수 제한이 없습니다. 가짜 가입도 Supabase의 기본 제한에만 의존합니다.
- **직접 할 일**
  - **Authentication → Rate Limits**에서 가입·로그인 시도 제한 값을 확인합니다. 기본값을 높이지 않습니다.
  - 공개 운영 전에 이메일 확인(Confirm email)을 다시 켭니다. 확인하지 않은 계정은 댓글을 쓸 수 없게 됩니다.
  - CAPTCHA(로봇 방지)는 **혼자 켜지 않습니다.** Supabase에서만 켜면 홈페이지의 가입·로그인이 모두 막힙니다. 홈페이지 코드에 함께 넣어야 하므로 필요할 때 개발 요청으로 진행합니다.

### 5.5 악성 글이나 스크립트를 넣는 경우

- **무슨 일이 생기나**: 댓글·문의에 스크립트를 넣어 다른 방문자나 관리자의 브라우저에서 실행시키려는 시도입니다.
- **이미 되어 있는 것**: 내용은 화면에 글자로만 표시합니다. 관리자 화면도 같습니다. 문의 알림 메일도 글자 본문만 씁니다.
- **직접 할 일**: 문의나 댓글에 있는 링크를 관리자 계정으로 로그인한 브라우저에서 바로 열지 않습니다.

### 5.6 이미지 저장소 악용

- **무슨 일이 생기나**: 로그인한 회원이 부적절한 이미지를 올리거나, 저장 용량을 채우려 할 수 있습니다.
- **이미 되어 있는 것**: 로그인 회원만, 본인 폴더에만, 5MB 이하의 이미지 형식만 올릴 수 있습니다. 댓글 자체가 10분 5개로 제한됩니다. 관리자가 댓글을 삭제하면 이미지도 지웁니다.
- **직접 할 일**: 신고가 들어온 댓글을 관리자 화면에서 처리합니다. Supabase의 **Storage** 화면에서 용량을 가끔 확인합니다.

### 5.7 개인정보가 새는 경우

- **무엇이 개인정보인가**: 회원 이메일, 문의의 이메일과 내용, 출시 알림 신청 이메일입니다.
- **이미 되어 있는 것**: 방문자와 일반 회원은 이 정보를 읽을 수 없습니다. 관리자 출시 알림 화면은 이메일을 보여 주지 않고 게임별 수만 보여 줍니다. 서버 기록에는 문의 내용이나 이메일을 남기지 않습니다.
- **직접 할 일**
  - 처리가 끝난 문의는 정한 보관 기간이 지나면 지웁니다(보관 기간은 아직 정하지 않았습니다. `docs/ROADMAP.md` 6-B).
  - Supabase 화면이나 관리자 화면을 캡처해 공유할 때 이메일이 보이지 않게 합니다.
  - Supabase는 해외 사업자입니다(저장 지역은 서울). 공개 운영 전에 개인정보처리방침에 처리 위탁과 국외 이전을 어떻게 적어야 하는지 법률 검토를 받습니다.

### 5.8 데이터가 사라지는 경우

- **무슨 일이 생기나**: 실수로 지우거나, 계정을 빼앗겨 지워지거나, 프로젝트가 삭제되는 경우입니다.
- **지금 상태**: 무료 요금제에는 **자동 백업이 없습니다.** 지운 데이터를 되돌릴 방법이 없습니다.
- **직접 할 일**
  - 중요한 표(뉴스, 상품, 문의, 출시 알림 신청)는 **Table Editor**에서 표를 열고 내보내기(CSV)로 가끔 저장해 둡니다. 내보낸 파일에는 이메일이 들어 있으니 안전한 곳에 둡니다.
  - 공개 운영을 시작하면 유료(Pro, 월 $25부터) 전환을 검토합니다. 매일 자동 백업이 됩니다.
  - 표 구조와 권한은 `supabase/migrations/`에 있으므로 언제든 새 프로젝트에 다시 만들 수 있습니다(`pnpm supabase:sql`). 사라지면 곤란한 것은 표 안의 내용입니다.

### 5.9 서비스가 멈추는 경우

- **무슨 일이 생기나**: 무료 요금제는 1주일 동안 사용이 없으면 일시정지됩니다. 한도를 넘으면 제한이 걸립니다.
- **이미 되어 있는 것**: Supabase에 연결할 수 없어도 홈페이지의 정적 화면(메인, 게임 소개, 로드맵)은 그대로 보이고, 뉴스·상품은 시연 내용과 안내를 보여 줍니다.
- **직접 할 일**: 일시정지 안내 메일이 오면 Supabase 화면에서 다시 켭니다. 공개 운영 중에는 유료 전환이 안전합니다.

## 6. 문제가 생겼을 때

### 6.1 키나 비밀번호가 샌 것 같을 때

1. Supabase의 **Project Settings → API Keys**에서 샌 키를 폐기하고 새로 발급합니다. 비밀 키가 샜다면 비밀 키를, 데이터베이스 비밀번호가 샜다면 **Database 설정**에서 비밀번호를 바꿉니다.
2. `.env.local`과 배포 환경 변수의 값을 새 값으로 바꾸고 서버를 다시 시작합니다.
3. `pnpm services:check`로 확인합니다.
4. **Authentication → Users**와 표 내용을 보고 모르는 계정이나 변경이 없는지 확인합니다.
5. GitHub에 올라갔다면 올린 기록을 지우는 것보다 **키 교체가 먼저**입니다. 한 번 올라간 값은 이미 복사됐다고 봅니다.

공개 키는 새도 교체할 필요가 없습니다.

### 6.2 관리자 계정이 뚫린 것 같을 때

1. Supabase 화면의 **Authentication → Users**에서 관리자 계정의 비밀번호를 바로 바꿉니다.
2. 같은 화면의 사용자 메뉴에 계정을 잠시 정지하는 기능이 있으면 정지해 둡니다(메뉴 구성은 바뀔 수 있습니다). 비밀번호를 바꾼 뒤에도 이미 로그인된 브라우저는 잠시 유지될 수 있으므로, 급하면 6.4절처럼 프로젝트를 일시정지합니다.
3. 관리자 화면에서 뉴스·상품·댓글 처리 기록에 모르는 변경이 없는지 봅니다. 댓글 처리는 `moderation_actions` 표에 기록이 남습니다.
4. Supabase 계정 자체가 의심되면 Supabase 계정 비밀번호를 바꾸고 2단계 인증을 켠 뒤 6.1절을 모두 진행합니다.

### 6.3 스팸이 몰려올 때

1. 댓글: 관리자 화면에서 숨김·삭제합니다. 반복되는 낱말은 금칙어에 추가합니다(금칙어는 화면 목록과 데이터베이스 표를 함께 고쳐야 하므로 개발 요청으로 진행).
2. 가짜 가입: **Authentication → Sign In / Providers**에서 가입을 잠시 막을 수 있습니다(새 가입 허용 끄기).
3. 문의·출시 알림: 6.4절의 방법으로 잠시 닫고 원인을 확인합니다.

### 6.4 급하게 전부 멈춰야 할 때

- 가장 빠른 방법은 Supabase의 **Project Settings → General**에서 프로젝트를 일시정지하는 것입니다. 홈페이지는 시연 내용으로 계속 보이고, 로그인·댓글·문의 저장만 멈춥니다. 데이터는 그대로 남습니다.
- 다시 켜기 전에 원인을 확인하고 키를 교체합니다.

## 8. 아직 남아 있는 약점

숨기지 않고 적어 둡니다. 급한 순서입니다.

1. **자동 백업이 없습니다.** 무료 요금제의 한계입니다. 수동 내보내기나 유료 전환이 필요합니다.
2. **문의 표에 직접 넣는 요청은 횟수 제한이 없습니다.** 홈페이지를 거치면 10분 5회로 막지만, 공개 키로 Supabase에 직접 보내면 계속 넣을 수 있습니다. 읽을 수는 없으므로 정보 유출은 아니고 문의함이 가짜 글로 채워지는 문제입니다. 데이터베이스 쪽 제한을 추가하거나 문의 저장을 서버 전용으로 바꾸는 개선이 가능합니다.
3. **가짜 가입을 막는 장치가 Supabase 기본 제한뿐입니다.** 공개 운영 전에 이메일 확인을 켜고, 필요하면 CAPTCHA를 홈페이지에 넣습니다.
4. **출시 알림 신청도 직접 요청으로 가짜 주소를 넣을 수 있습니다.** 확인하지 않은 주소에는 소식을 보내지 않으므로 피해는 표에 쓸모없는 행이 쌓이는 데 그칩니다.
5. **홈페이지 서버의 요청 횟수 제한은 서버 한 대의 메모리 기준입니다.** 배포 환경에서 서버가 여러 대로 늘어나면 제한이 느슨해집니다.
6. **성인 게임 확인은 법적 본인인증이 아닙니다.** 실제 성인 콘텐츠를 공개하기 전에 본인인증 서비스가 필요합니다(`docs/EXTERNAL-SERVICES.md` 9번).
7. **관리자 판정 함수(`is_admin`)는 방문자도 실행할 수 있습니다.** 자기 자신이 관리자인지만 알려 주므로(방문자에게는 항상 아니오) 위험은 없지만, 의도와는 다릅니다.
8. **로그인한 회원의 동작은 실제 프로젝트에서 아직 확인하지 못했습니다.** 시험용 데이터베이스의 자동 검사로만 확인했습니다.
9. **통합 계정을 켜면 다른 서비스용 로그인 토큰이 홈페이지에서 회원 본인과 같은 권한을 가집니다.** Supabase의 OAuth 2.1 서버가 발급하는 토큰이 회원 본인의 토큰과 같은 방식으로 권한 검사를 통과하기 때문입니다. 그래서 직접 만든 서비스만 클라이언트로 등록하고, 회원 탈퇴와 서비스 연결 기록 삭제는 서비스 토큰으로 할 수 없게 막았습니다. 댓글 쓰기 같은 나머지 동작은 막지 않았으므로, 외부 회사의 서비스를 등록하게 되면 표별 정책에 클라이언트 조건을 더해야 합니다. 이 기능은 Supabase의 베타 기능이며 실제 프로젝트에서 아직 확인하지 않았습니다(`docs/UNIFIED-ACCOUNT.md`).
