# DEVFORGE 개발 로드맵

2026년 10월 3일에 정리한 단계별 개발 방향입니다. 공통 구조를 먼저 만들고 기능을 차례로 덧붙입니다. 각 단계는 **개발 계획 → 개발 → 다음 단계 계획** 순서로 진행하고, 단계가 끝나면 이 문서의 상태를 고칩니다.

## 0단계. 기반 정리와 공통 구조 (완료)

뒤 단계들이 같은 도구를 쓰도록 흩어진 것을 모으고 남은 정리를 끝냅니다.

- 페이지 적용 도구 통합: 공통 헤더·검색 설명·번역 준비 스크립트를 `pnpm pages:apply` 한 번으로 적용하고, 빠진 곳은 `pnpm pages:check`와 자동 검사가 알려 줍니다. 사이트맵 목록 누락도 검사합니다.
- 서버 공통 도구: 요청 횟수 제한(`lib/http/rate-limit.ts`)과 JSON 요청·응답 도구(`lib/http/json.ts`). 문의 양식(1단계), 댓글 제한(4단계), 출시 알림(5단계)이 함께 씁니다.
- 정적 페이지 공통 양식 전송 도구(`public/form-submit.mjs`): 전송 중 표시, 입력 오류 안내, 요청 제한·연결 실패 안내를 한곳에서 처리합니다.
- 정리: 쓰이지 않던 `public/project-detail.css` 삭제, 파일 지도의 빠진 테스트 설명 보충, 약관·개인정보 화면에 "영어 화면은 참고용 번역, 한국어 원문 우선" 안내 추가.

## 1단계. 문의 양식 (완료)

문의하기 페이지에 양식을 추가했습니다. 화면과 검증을 먼저 만들었고 접수 알림·답변 메일 발송은 7단계에서 연결합니다. 문의 보관 기간은 운영 전에 정해야 합니다(6단계 결정 항목).

- 화면: 분류(게임·계정·굿즈·개인정보·기타), 이메일, 제목, 내용, 개인정보 수집 동의. 0단계의 양식 전송 도구 사용
- 서버: `POST /api/contact` — 입력 검증, 요청 횟수 제한, 자동 입력 방지(숨김 칸)
- 저장: 설정이 없으면 "시연 모드(저장하지 않음)"로 응답, Supabase 설정이 있으면 `contact_messages` 테이블에 저장(마이그레이션 준비)
- 관리자: 문의함 목록과 처리 상태(대기·답변 완료), 데모 화면 포함
- 영어 사전과 개인정보처리방침의 수집 항목 안내 추가

## 2단계. 로드맵 페이지 (완료)

이미 있는 게임 데이터로 개발 현황을 한눈에 보여 줍니다. 확정되지 않은 날짜는 넣지 않았습니다.

- `public/roadmap.html`: 대표(6)·개발 중(26)·기획(1)·보류(2) 묶음, 장르 필터와 주소 저장(`?genre=`), 게임 소개 연결, 성인 확인 필요 표시(이미지는 쓰지 않음)
- 메인의 개발 현황판과 서랍 메뉴에서 연결, 공통 헤더·사이트맵·영어 사전 등록(0단계 도구 사용). 상단 주요 메뉴는 그대로 두었습니다.
- 함께 고친 것: 메인 게임 목록에서 장르 버튼에 걸리지 않던 11개 프로젝트가 '기타'에 나오도록 필터용 대표 장르 규칙(`getFilterGenre`)을 추가했고, 장르 이름표를 `public/game-projects.mjs` 한 곳으로 모았습니다.

## 3단계. 개발 뉴스 검색·분류 (완료)

이미 있던 종류 버튼에 검색과 조건 표시를 더했습니다. 메인 게임 목록의 조건 칩·초기화 방식을 그대로 따릅니다.

- `public/devlog.html`: 검색 칸(제목·요약·종류 이름), 적용 중인 조건 칩과 초기화 버튼, 결과 수("2개의 뉴스 · 전체 4개 중"), 초기화 버튼이 있는 결과 없음 안내
- 조건은 주소에 저장합니다(`?q=&type=`). 새로고침·공유·뒤로 가기에서 복원하고, 허용되지 않은 값은 버립니다.
- 시연 뉴스와 서버 뉴스에 같은 조건을 적용합니다. 영어 화면에서는 한국어 원문과 영어 번역 양쪽으로 찾습니다.
- 함께 고친 것: 영어 화면에서 한글 검색어를 넣으면 조건 칩이 번역되지 않던 문제(메인 게임 목록 포함)를 번역기의 "입력 유지" 형식(`keep`)으로 고쳤습니다.
- 미룬 것: 게임별 필터(`game=`). 뉴스 데이터에 "어느 게임 소식인지" 항목이 없어 관리자 작성 화면과 데이터베이스 항목 추가가 먼저 필요합니다.

## 4단계. 댓글 작성 제한 (완료)

도배와 부적절한 댓글을 막는 규칙을 넣었습니다. 수치와 금칙어는 한곳(`lib/comments/guard.ts`, `lib/comments/banned-words.ts`)에서 고칩니다.

- 규칙: 30초에 1개, 10분에 5개, 24시간 안 같은 내용 금지, 링크 2개까지, 금칙어(띄어 써도 찾음)
- 시연(로컬) 댓글과 Supabase 댓글이 같은 규칙을 씁니다. 막히면 이유와 다시 쓸 수 있는 시간을 알려 주고, 내용 문제는 입력 칸에 표시합니다.
- 데이터베이스 쪽 제한: 일곱 번째 마이그레이션(`202610040002_comment_limits.sql`)이 같은 수치·금칙어로 화면을 우회한 요청도 막습니다. 실행은 Supabase 연결 때(7단계) 합니다.
- 관리자 댓글 관리: 지금 규칙으로는 등록되지 않는 기존 댓글에 "자동 감지" 사유를 표시합니다. 막힌 댓글은 저장되지 않으므로 따로 목록이 없습니다.
- 넣지 못한 것: 주소(IP)별 제한. 댓글이 우리 서버를 거치지 않고 Supabase로 바로 저장되어 주소를 알 수 없습니다. 회원별 제한만 적용합니다.
- 함께 고친 것: 영어 화면에서 한글 닉네임이 들어간 문구(댓글 작성 이름표·회원 메뉴·신고 사유 이름)가 번역되지 않던 문제.

## 5단계. 출시 알림 신청 (완료)

게임 소개 페이지에서 "출시되면 알려 주세요"를 이메일로 신청받습니다. 신청을 받아 두는 데까지 만들었고, 메일 발송은 7단계에서 연결합니다.

- 대상: 35개 가운데 30개. 성인 게임 3개(H·U·V)는 본인인증 전이라 양식을 넣지 않았고, 보류 게임 2개(γ·ζ)는 "지금은 신청을 받지 않는다"는 안내만 보여 줍니다. 판정은 `getReleaseNotifyState` 한 곳에서 합니다.
- 화면: 게임 소개 35개 첫 화면에 `/release-notify.mjs` 한 줄만 붙이고, 스크립트가 대상 게임에만 양식(이메일·수신 동의)을 넣습니다.
- 서버: `POST /api/notify`(10분 5회 제한·검증·자동 입력 방지), `POST /api/notify/unsubscribe`와 수신 거부 화면(`/notify/unsubscribe`, 버튼을 눌러야 처리)
- 저장 준비: 여덟 번째 마이그레이션(`202610040003_release_notifications.sql`). 방문자는 표를 직접 열 수 없고 신청·수신 거부 함수로만 바꿉니다. 같은 게임·같은 이메일은 한 번만 저장합니다.
- 관리자: `/admin/notify`에서 게임별 신청 수만 봅니다(이메일 주소는 표시하지 않음). 데모는 `/admin/demo?form=notify`.
- 7단계에서 할 일: 메일을 보내기 전에 확인 메일로 본인 신청인지 먼저 확인합니다(남의 이메일로 신청하는 장난 방지, `confirmed_at` 열 준비됨). 신청 보관 기간은 6단계에서 정합니다.

## 6단계. 내용 반영

### 6-A. 오해 소지 문구 정리 (완료)

확정되지 않은 내용을 사실처럼 보이게 하던 표기를 걷어 내고, 시연 내용에는 "시연" 표시를 붙였습니다. 새 내용을 지어내지는 않았습니다.

- 굿즈(메인·굿즈 페이지 각 8개): 임의 가격을 "가격 미정"으로, 가짜 할인(취소선 정가·할인율 배지) 제거, NEW·HOT·LIMITED 배지를 "시연" 배지로 교체, 상품 이름의 "한정판" 제거
- 메인 굿즈 카드: 판매처가 아닌 스마트스토어 첫 화면으로 가던 링크를 없애고 "준비 중" 카드로 바꿈, "화면 검증용 목업" 안내 추가, 쓰이지 않게 된 임시 링크 처리 코드와 할인 스타일 제거
- 시연 뉴스(메인·뉴스 목록·뉴스 상세): 카드와 상세에 "시연" 표시 추가, 메인 요약의 지어낸 수치("반응 속도 40% 향상", "신규 레벨 12개", "이슈 7건", "FPS 15% 향상")와 "플레이어들이 보고한" 같은 표현 제거
- 메인 통계: "개발 뉴스 4"를 "시연 뉴스 4"로 변경(실제 뉴스가 등록되면 서버 값과 원래 문구로 되돌림)
- `tests/demo-content.test.mjs`가 임의 가격·가짜 할인·판매 유도 배지·지어낸 수치가 다시 들어오지 않는지 검사합니다.

### 6-B. 정해 주셔야 하는 것 (결정 대기)

점검하면서 찾았지만 내용 결정이 필요해 고치지 않은 것입니다. 위에서부터 급한 순서입니다.

1. 프로젝트 C(카오스폰즈) 소개 페이지의 확정되지 않은 표기
   - "Steam 2026 Q3 예정 · v0.1.0 Early Access": 2026년 3분기는 이미 지났습니다. 메인의 "확정된 출시 일정은 없습니다" 안내와도 어긋납니다.
   - "가격 ₩11,000 (기본 출시가)", "PC (Steam)"
   - "15세 이용가 (예상)" 배지: 등급 분류를 받기 전에 등급 표시처럼 보이는 그림을 쓰는 것은 피하는 편이 안전합니다.
2. 굿즈에 쓰인 게임 이름(아비스 크로니클·네온 펄스·루나 점프·에코 보이드): 공개 프로젝트 35개에 없는 이름입니다. 실제 프로젝트 이름으로 바꿀지, 굿즈 구역을 실제 상품이 정해질 때까지 접어 둘지 결정이 필요합니다. 가격과 판매처도 함께 정합니다.
3. 시연 뉴스 4개의 게임 이름(에코 보이드·스타 베이그런트·네온 펄스·블레이드 리프트), 버전 표기(v0.8, v2.1.3 패치)와 2025년 3~4월 날짜: 실제 소식으로 바꿀지, 실제 소식이 생길 때까지 시연 뉴스를 숨길지 결정이 필요합니다.
4. 커뮤니티 안내의 "베타 테스터 모집"(메인 Discord 카드), "개발 공지와 베타 테스트 모집"(커뮤니티 페이지): 실제 계획이 없다면 빼야 합니다.
5. 게임 소개 28개의 실제 소개 내용, 프로젝트 δ·θ 연령 등급, 프로젝트 L "CV : 미정" 표기, 프로젝트 D 이미지와 개발 문구
6. 문의 양식·출시 알림 신청으로 받는 이메일의 보관 기간
7. 약관·개인정보처리방침 본문과 운영자 정보 확정
8. 프레스 키트, 팀·스튜디오 소개, 채용 페이지를 만들지 여부와 내용
9. 관리자 메뉴의 `DEVFORGE` 표기

## 7단계. 외부 서비스 연결

2026년 10월 4일부터 가입이 무료인 서비스(Supabase 무료, Resend 무료, Google·카카오·Discord 로그인, YouTube API, GA4)의 연결 준비를 먼저 진행합니다. 가입 자체에 비용이 드는 것(도메인, Apple 로그인, 본인인증, 자체 결제)과 유료 요금제는 따로 정한 뒤에 진행합니다.

준비 1(완료): 값만 넣으면 동작하도록 빠져 있던 부분을 채웠습니다.

- 메일 발송 기반(`lib/mail/`): Resend로 글자 본문 메일을 보내며, 세 값(`RESEND_API_KEY`·`MAIL_FROM`·`CONTACT_NOTIFY_EMAIL`)이 모두 올바를 때만 켜집니다.
- 문의 접수 알림: 문의가 저장되면 운영자 메일로 알림을 보냅니다(답장 주소는 문의한 사람). 도메인이 없어도 Resend 가입 이메일로는 받을 수 있습니다.
- `pnpm services:check`: Supabase·메일·YouTube·GA4의 연결 상태와 다음에 할 일을 한 번에 보여 줍니다.
- README에 "무료 서비스부터 연결하는 순서"와 "메일 발송 연결" 안내를 추가했습니다.

준비 2(완료): 출시 알림 확인 메일(본인 신청 확인)을 준비했습니다.

- 신청이 저장되면 확인 메일을 보내고, 메일의 주소에서 버튼을 누르면 "확인 완료"가 됩니다(`/notify/confirm`). 확인을 마친 주소에만 출시 소식을 보냅니다.
- 켜지는 조건: 인증한 도메인의 보내는 주소(유료 도메인 필요)와 Supabase 서버 전용 비밀 키(`SUPABASE_SECRET_KEY`). 둘 중 하나라도 없으면 지금처럼 신청만 받아 둡니다.
- 남용 방지: 같은 신청에는 24시간에 한 번, 같은 이메일로는 하루 3통까지. 확인 값 발급은 서버 전용 키만 할 수 있습니다.
- 여덟 번째 마이그레이션에 확인 메일 발송 시각, 확인 값 발급·본인 확인 함수, 집계의 확인 완료 수를 더했습니다(아직 어디에도 적용하지 않은 파일이라 새 파일을 만들지 않고 고쳤습니다).
- 관리자 화면에 "확인 완료" 수를 추가했고, `pnpm services:check`에 "출시 알림 확인 메일" 항목을 추가했습니다.
- 아직 없는 것: 출시 소식 자체를 보내는 기능(확인 완료 주소 대상 발송). 도메인을 마련한 뒤 만듭니다.

준비 3(완료): 데이터베이스 파일을 가입 전에 미리 실행해 봤습니다.

- 마이그레이션 여덟 개를 시험용 PostgreSQL(PGlite 18)에서 README 순서대로 실행해 오류가 없음을 확인했습니다.
- 방문자·회원·관리자·서버 전용 키 역할로 바꿔 가며 권한과 제한(댓글 작성 제한, 문의, 출시 알림 확인 값·하루 한도, 탈퇴)을 확인하는 검사(`tests/supabase-migrations.test.mjs`)를 추가했습니다. `pnpm check`에 포함됩니다.
- Supabase의 인증·저장소는 필요한 부분만 흉내 낸 것입니다. 실제 프로젝트 적용 뒤 로그인·이미지 업로드를 한 번 더 확인합니다.

2026년 10월 4일 실제 연결: Supabase 프로젝트(서울, 무료 요금제)를 만들고 주소·공개 키·관리자 이메일을 넣은 뒤 데이터베이스 설정을 적용했습니다. 문의와 출시 알림이 실제로 저장되는 것, 방문자에게 막혀 있어야 하는 쓰기·읽기·이미지 올리기가 모두 거부되는 것을 확인했습니다. 연결 상태와 보안 대비책은 `docs/SUPABASE-GUIDE.md`에 정리했습니다. 로그인한 회원의 동작(가입, 댓글, 이미지)은 직접 가입해 확인해야 합니다.
