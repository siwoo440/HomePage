# 통합 계정 안내

Palettra Games 홈페이지 계정 하나로 Mate | Verse, Atelier | Verse 같은 서비스에 로그인하기 위한 구조와 설정 순서입니다. 작성일은 2026년 10월 8일입니다.

- 방식(2026-10-08 사용자 결정): 서비스마다 Supabase 프로젝트는 따로 두고, 로그인만 홈페이지 계정으로 통합합니다.
- 로그인 유지(2026-10-08 사용자 결정): 서비스마다 처음 한 번씩 로그인합니다. 한 번 로그인하면 모든 서비스가 로그인되는 방식은 도메인을 정한 뒤 검토합니다.
- 현재 상태: 홈페이지 쪽 코드와 데이터베이스 정의만 준비했습니다. 실제 Supabase 프로젝트 설정과 서비스 쪽 연결은 하지 않았고, 실제 서비스에서 동작을 확인한 적이 없습니다. 자동 검사는 대체 연결과 시험용 PostgreSQL로만 확인합니다.

---
## 1. 구조

홈페이지의 Supabase 프로젝트가 로그인 제공자(OAuth 2.1 서버) 역할을 하고, 각 서비스의 Supabase 프로젝트는 홈페이지를 "사용자 지정 로그인(OIDC)"으로 등록합니다. Google 로그인과 같은 구조에서 Google 자리에 홈페이지가 들어갑니다.

1. 이용자가 서비스에서 "Palettra 계정으로 로그인"을 누릅니다.
2. 서비스의 Supabase가 홈페이지 Supabase의 로그인 주소로 보냅니다.
3. 홈페이지 Supabase가 이용자를 홈페이지의 `/oauth/consent` 화면으로 보냅니다.
4. 로그인하지 않았다면 `/login`에서 로그인한 뒤 같은 화면으로 돌아옵니다.
5. 이용자가 서비스 이름과 넘어가는 정보를 확인하고 허용합니다. 이미 허용한 서비스는 묻지 않고 넘어갑니다.
6. 서비스의 Supabase가 이용자를 서비스 계정으로 로그인시킵니다. 서비스 프로젝트에는 서비스 전용 회원 행이 만들어지고, 홈페이지 회원 번호가 연결 정보로 남습니다.
7. 서비스가 홈페이지에 이용 기록을 남깁니다(선택). 홈페이지의 내 정보에 서비스와 이용일이 보입니다.

서비스의 채팅·맵 같은 내용은 서비스 프로젝트에만 있고 홈페이지 프로젝트에는 들어오지 않습니다. 비밀번호도 서비스로 넘어가지 않습니다.

## 2. 홈페이지가 제공하는 것

| 항목 | 위치 | 내용 |
| --- | --- | --- |
| 로그인 허용 화면 | `/oauth/consent` (`app/oauth/consent/`) | 서비스 이름, 돌아갈 주소, 서비스가 받는 정보를 보여 주고 허용·거부. 로그인과 닉네임·약관 동의를 마친 회원만 허용 가능 |
| 내 정보: 계정 기본 정보 | `/account` (`app/account/account-connections.tsx`) | 이메일, 이메일 인증 여부, 가입일, 마지막 로그인 |
| 내 정보: 로그인 연동 | 같은 파일 | 연결된 로그인 방법(이메일·간편 로그인) 목록, 간편 로그인 연결·해제. 마지막 로그인 방법과 이메일 로그인은 해제하지 않음 |
| 내 정보: 연결된 서비스 | 같은 파일 | 홈페이지와 Verse 계열 서비스의 상태(지금 이용 중·연결됨·연결 가능·준비 중), 연결일, 처음·마지막 이용일, 서비스 요약, 연결 해제 |
| 처리 코드 | `lib/member/connections.ts`, `lib/member/services.ts`, `lib/member/oauth-consent.ts` | 로그인 연동, 서비스 목록 구성, 로그인 허용 처리 |
| 데이터베이스 | `supabase/migrations/202610080001_account_services.sql` | 서비스 목록(`account_services`), 서비스 연결 기록(`member_service_links`), 이용 기록 함수(`record_service_use`), 서비스 로그인의 회원 탈퇴 차단 |

서비스 이름과 주소는 `scripts/verse-services.mjs`의 목록을 그대로 씁니다. 서비스가 통합 계정에 연결되었는지는 `account_services` 표에 OAuth 클라이언트 식별자가 들어 있는지로 판단합니다.

연결된 서비스의 상태는 다음과 같이 정합니다.

| 상태 | 조건 |
| --- | --- |
| 지금 이용 중 | 홈페이지 |
| 연결됨 | 이 계정으로 로그인을 허용했거나 이용 기록이 있는 서비스 |
| 연결 가능 | OAuth 클라이언트가 등록되어 있고 접속 주소가 정해진 서비스 |
| 준비 중 | 위에 해당하지 않는 서비스 |

## 3. 설정 순서

Supabase 화면에서 하는 일은 사용자가 직접 합니다. 키와 비밀 값은 채팅·문서·커밋에 적지 않습니다.

### 3.1 홈페이지 프로젝트

1. SQL Editor에서 `supabase/migrations/202610080001_account_services.sql`을 실행합니다. 이미 앞의 아홉 파일을 적용한 프로젝트는 이 파일만 실행합니다.
2. **Authentication → Sign In / Providers**에서 "Allow manual linking"을 켭니다. 내 정보의 간편 로그인 연결에 필요합니다.
3. **Project Settings → JWT Keys**에서 서명 방식을 비대칭 키(ES256 또는 RS256)로 바꿉니다. 로그인 제공자가 만드는 신원 확인 토큰에 필요합니다.
4. **Authentication → OAuth Server**를 켜고 Authorization Path에 `/oauth/consent`를 넣습니다. **Authentication → URL Configuration**의 Site URL이 홈페이지 주소여야 합니다.
5. **Authentication → OAuth Apps**에서 서비스마다 클라이언트를 등록합니다. 이름은 서비스 이름, 종류는 Confidential, Redirect URI는 3.2의 2번에서 확인한 주소입니다. 클라이언트 식별자와 비밀 값이 나옵니다.
6. SQL Editor에서 서비스와 클라이언트를 이어 줍니다.

```sql
update public.account_services -- 서비스 목록 수정
set oauth_client_id = '등록한-클라이언트-식별자' -- OAuth 클라이언트 연결
where id = 'mate-verse'; -- 연결할 서비스 선택
```

### 3.2 서비스 프로젝트

1. **Authentication → Providers → New Provider → Auto-discovery (OIDC)**를 고릅니다.
2. 식별자는 `custom:palettra`, Issuer URL은 `https://홈페이지-프로젝트-식별자.supabase.co/auth/v1`, 요청 정보는 `openid email`로 넣습니다. 화면에 나오는 Callback URL을 3.1의 5번 Redirect URI에 등록합니다.
3. 3.1의 5번에서 받은 클라이언트 식별자와 비밀 값을 넣고 켭니다. 비밀 값은 이 화면에만 넣고 서비스 코드나 환경 변수에는 넣지 않습니다.

### 3.3 확인

1. 서비스에서 "Palettra 계정으로 로그인"을 눌러 홈페이지의 허용 화면이 뜨는지 확인합니다.
2. 허용한 뒤 서비스에 로그인되는지 확인합니다.
3. 홈페이지 `/account`의 연결된 서비스에 "연결됨"과 연결일이 보이는지 확인합니다.
4. 연결 해제를 누른 뒤 서비스에서 다시 로그인하면 허용 화면이 다시 뜨는지 확인합니다.

## 4. 서비스가 지킬 약속

서비스 저장소(Mate | Verse는 ChatBot 저장소, Atelier | Verse는 VR 저장소)에서 구현할 때의 기준입니다.

- 로그인 시작: Supabase의 간편 로그인과 같은 방법으로 `custom:palettra`를 요청합니다. `supabase-js`는 `signInWithOAuth({ provider: "custom:palettra" })`, 직접 호출하는 경우는 `/auth/v1/authorize?provider=custom:palettra`입니다.
- 요청 정보: `openid email`만 요청합니다. 이름과 사진(`profile`)은 필요할 때만 더합니다. 홈페이지 닉네임은 넘어가지 않으므로 서비스 안 닉네임은 서비스가 따로 받습니다.
- 이용 기록: 로그인 직후 응답에 들어 있는 홈페이지 쪽 접근 토큰(`provider_token`)으로 홈페이지 프로젝트의 `record_service_use` 함수를 한 번 호출합니다. 이 토큰은 로그인 직후에만 받을 수 있습니다.

```http
POST https://홈페이지-프로젝트-식별자.supabase.co/rest/v1/rpc/record_service_use
apikey: 홈페이지-공개-키
Authorization: Bearer 로그인-직후-받은-provider_token
Content-Type: application/json

{ "service_summary": { "nickname": "서비스 안 닉네임", "plan": "무료", "adult_verified": false } }
```

- 요약 항목: `nickname`(40자), `plan`(40자), `adult_verified`(참·거짓)만 홈페이지 화면에 표시합니다. 그 밖의 값은 저장되어도 표시하지 않습니다. 전체 크기는 2,000바이트 이하입니다. 대화 내용 같은 민감한 정보는 넣지 않습니다.
- 홈페이지 토큰의 사용 범위: 이용 기록 함수 호출에만 씁니다. 이 토큰은 홈페이지에서 회원 본인과 같은 권한을 가지므로 저장하지 않고, 다른 용도로 쓰지 않습니다.
- 탈퇴: 서비스에서의 탈퇴는 서비스 프로젝트의 회원과 내용만 지웁니다. 홈페이지 계정 탈퇴는 홈페이지에서 직접 로그인했을 때만 가능합니다(서비스 로그인으로 호출하면 `HOMEPAGE_ONLY`로 거부). 홈페이지에서 탈퇴해도 서비스에 저장된 내용은 지워지지 않으므로 서비스에서 따로 지워야 합니다.
- 연결 해제: 홈페이지에서 연결을 해제하면 허용이 취소되고 이용 기록이 지워집니다. 서비스에 이미 로그인된 상태는 서비스 프로젝트의 것이라 바로 끊기지 않습니다.

## 5. Mate | Verse 저장소에서 할 일

ChatBot 저장소는 Supabase 인증을 브라우저에서 직접 호출하고, Google·카카오 로그인 버튼을 Supabase 설정에 따라 표시합니다(2026-10-08 확인). 통합 계정은 여기에 로그인 방법 하나를 더하는 일입니다.

1. 지원 로그인 목록에 `custom:palettra`를 더하고 버튼 문구를 "Palettra 계정으로 로그인"으로 표시합니다.
2. 로그인 복귀 처리에서 응답의 `provider_token`을 받아 4절의 이용 기록 함수를 한 번 호출합니다. 실패해도 로그인은 계속합니다.
3. 홈페이지 프로젝트 주소와 공개 키를 환경 변수로 더합니다. 값이 없으면 이용 기록 호출을 건너뜁니다.
4. 설정의 계정 관리 화면에 "Palettra 계정으로 로그인함"과 홈페이지 내 정보로 가는 링크를 표시합니다.
5. 그 저장소의 문서(`docs/ACCOUNT-SETUP.md`)에 적힌 "홈페이지와 프로젝트 분리" 결정은 그대로 유지됩니다.

## 6. 알아 둘 점

- OAuth 2.1 서버는 Supabase의 베타 기능입니다(2026-10-08 문서 기준, 모든 요금제에서 무료). 화면 이름과 동작이 바뀔 수 있습니다.
- 사용자 지정 로그인은 무료 요금제에서 프로젝트당 3개까지 등록할 수 있습니다.
- 홈페이지가 발급한 서비스용 토큰은 홈페이지 데이터에 대해 회원 본인과 같은 권한을 가집니다. 그래서 직접 만든 서비스만 클라이언트로 등록하고, 회원 탈퇴와 이용 기록 삭제는 서비스 토큰으로 할 수 없게 막았습니다.
- 내 정보의 "연결 가능" 상태는 클라이언트 등록 여부만 봅니다. 서비스 쪽 설정이 끝났는지는 3.3의 순서로 직접 확인합니다.
- 한 번 로그인으로 모든 서비스가 로그인되게 하려면 모든 서비스가 같은 도메인의 하위 주소를 써야 합니다. 도메인을 정한 뒤 다시 검토합니다.
