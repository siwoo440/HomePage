# DEVFORGE 로컬 완성형 기반 1단계 설계

## 1. 문서 목적

이 문서는 게임·상품·외부 계정이 준비되지 않은 현재 단계에서 DEVFORGE 홈페이지를 안정적으로 개발하고 검증할 수 있도록 1단계 개발 기반을 정리한다. 이후 프로젝트 콘텐츠, Supabase, 로그인, YouTube, GA4와 배포 기능을 추가할 때 기존 화면을 다시 만들지 않도록 작업 범위와 완료 기준을 고정한다.

## 2. 확정된 제품 방향

- 로컬 완성도를 먼저 확보한 뒤 외부 서비스를 단계적으로 연결한다.
- 방문자 경험의 우선순위는 게임 프로젝트와 개발 역량, 개발 소식과 커뮤니티, 굿즈 판매 순서다.
- 대표 프로젝트 6개를 먼저 강조하고 전체 35개는 검색·필터로 제공한다.
- 실제 게임과 상품이 없는 동안에도 모든 주요 화면과 상태를 검증할 수 있어야 한다.
- 시연 데이터는 실제 운영 정보로 오해되지 않도록 명시적으로 표시한다.
- 외부 서비스 연결은 화면 변경이 아니라 공급자 어댑터 추가로 처리한다.

## 3. 전체 단계와 이번 범위

전체 개발은 다음 하위 프로젝트로 분리한다.

1. 개발 기반 안정화
2. 통합 콘텐츠 모델과 로컬 공급자
3. 게임 포트폴리오 경험
4. 개발 소식·커뮤니티·상품의 로컬 관리 흐름
5. 외부 서비스와 운영 배포

이번 설계와 다음 구현 계획의 범위는 1단계인 개발 기반 안정화로 제한한다. 콘텐츠 모델 변경, 화면 개편, Supabase 연결과 로그인 구현은 포함하지 않는다.

## 4. 현재 상태

현재 홈페이지 소스에는 255개 Node 테스트, TypeScript 설정과 Next.js 운영 빌드가 있다. 메인 화면, 프로젝트 35개, 대표 프로젝트 6개, 뉴스, 상품, 커뮤니티, 댓글, 관리자 화면과 연령 확인 구조가 구현되어 있다.

현재 개발 기반에는 다음 문제가 있다.

- 홈페이지 저장소 루트에 별도 프로젝트인 `ChatBot/`과 `Text-Play/`가 함께 존재할 수 있다.
- TypeScript의 포괄적인 포함 규칙이 별도 프로젝트 소스까지 검사할 수 있다.
- `pnpm` 11에서 `package.json`의 기존 `pnpm.overrides` 설정이 무시된다.
- `msw`와 `sharp`의 의존성 빌드 허용 정책이 확정되지 않아 설치가 실패 상태로 끝날 수 있다.
- `lint` 스크립트는 있으나 재현 가능한 ESLint 의존성과 설정이 완성되지 않았다.
- 개발 서버와 운영 빌드 실행 뒤 생성 파일이 추적 파일을 변경할 가능성이 있다.
- 테스트, 타입 검사, 린트와 빌드를 한 번에 실행하는 공식 검증 명령이 없다.
- 문서의 완료 상태와 현재 코드가 일부 일치하지 않는다.

## 5. 설계 원칙

### 5.1 저장소 경계

홈페이지 검증 명령은 홈페이지 소스만 대상으로 한다. `ChatBot/`과 `Text-Play/`는 별도 프로젝트로 취급하며 이동, 삭제, 수정하거나 홈페이지 빌드에 포함하지 않는다.

Git 무시 규칙과 TypeScript 제외 규칙은 서로 다른 목적을 가진다. Git 무시 규칙은 별도 프로젝트가 홈페이지 커밋에 섞이는 것을 막고, TypeScript 제외 규칙은 홈페이지 타입 검사 범위를 고정한다. 두 규칙을 각각 명시한다.

### 5.2 재현 가능한 도구 체인

지원 Node.js와 pnpm 버전을 문서와 패키지 설정에 명시한다. 새 환경에서 잠금 파일을 사용한 설치가 경고가 아닌 성공 상태로 끝나야 한다.

의존성 빌드 스크립트는 필요한 패키지만 명시적으로 허용한다. 광범위한 전체 허용은 사용하지 않는다. `pnpm` 설정은 현재 버전이 실제로 읽는 작업 공간 설정 위치에 둔다.

### 5.3 단일 검증 진입점

개발자는 개별 명령과 통합 명령을 모두 사용할 수 있어야 한다.

- `test`: Node 회귀 테스트
- `typecheck`: 홈페이지 TypeScript 검사
- `lint`: 홈페이지 소스 정적 검사
- `build`: Next.js 운영 빌드
- `check`: test, typecheck, lint, build 순차 실행

`check`는 첫 번째 실패에서 종료하고 어떤 단계가 실패했는지 명확히 보여준다. 로컬과 CI에서 동일한 명령을 사용한다.

### 5.4 생성 파일 안정성

개발 서버, 타입 생성과 운영 빌드를 실행한 뒤 추적 파일에 의도하지 않은 변경이 남지 않아야 한다. Next.js가 관리하는 파일은 공식 권장 방식에 맞춰 한 가지 형태로 고정하고, 직접 생성되는 캐시와 빌드 결과는 Git에서 제외한다.

### 5.5 기존 동작 보존

1단계는 개발 도구와 저장소 경계만 수정한다. 방문자 화면, 관리자 업무 규칙, 데모 데이터, API 응답과 CSS 시각 결과를 변경하지 않는다. 기존 255개 테스트는 동일하게 통과해야 한다.

## 6. 구성 요소별 변경 방향

### 6.1 패키지와 작업 공간 설정

`package.json`에는 실행 스크립트, 지원 패키지 관리자 정보와 필요한 개발 의존성을 둔다. pnpm 전용 해석·빌드 허용 설정은 `pnpm-workspace.yaml`에서 관리한다. 잠금 파일은 설정 변경 결과와 일치하도록 갱신한다.

### 6.2 TypeScript 범위

`tsconfig.json`은 홈페이지의 `app/`, `lib/`, `proxy.ts`, Next.js 생성 타입과 필요한 테스트 지원 타입만 검사한다. 별도 프로젝트, 설치 디렉터리, 빌드 캐시, 내부 보관 HTML과 임시 가져오기 폴더는 검사 대상에서 제외한다.

포괄적인 `**/*.ts` 규칙을 유지해야 한다면 별도 프로젝트 제외 목록을 명시하고 회귀 테스트로 검사한다.

### 6.3 ESLint

현재 Next.js와 TypeScript 버전에 맞는 ESLint와 설정 패키지 버전을 고정한다. 검사 범위는 홈페이지 소스와 스크립트로 제한하고 생성 파일, 보관 자료와 별도 프로젝트는 제외한다.

기존 코드 전체에 대규모 형식 변경을 일으키는 규칙은 도입하지 않는다. 실제 오류, 사용하지 않는 코드, 잘못된 React 사용과 위험한 전역 사용을 우선 검사한다. 현재 저장소의 Allman 스타일과 한글 주석 규칙은 자동 재정렬하지 않는다.

### 6.4 문서

`README.md`, `docs/DEVELOPMENT-GUIDE.md`, `docs/DEVELOPMENT-NOTES.md`에 공식 설치·검증 명령, 지원 버전, 별도 프로젝트 경계와 현재 완료 상태를 일치시킨다.

이미 구현된 다크 모드 연속 적용, 댓글 로컬 서비스와 공통 데이터 상태를 미완료로 설명하는 문구는 현재 코드와 테스트 결과에 맞게 수정한다.

## 7. 오류 처리

- 패키지 설치 실패는 네트워크, 잠금 파일, 빌드 허용과 버전 불일치를 구분해 출력한다.
- 별도 프로젝트 파일이 검사 범위에 들어오면 검증 테스트가 실패해야 한다.
- ESLint 설정이 없거나 실행 파일을 찾을 수 없으면 `check`가 성공으로 처리하지 않는다.
- 테스트, 타입 검사, 린트와 빌드 중 하나라도 실패하면 통합 검증 결과는 실패다.
- 외부 API 키가 없다는 이유로 1단계 검증이 실패해서는 안 된다.

## 8. 보안과 데이터 경계

- 비밀 키와 `.env.local`은 설치·검증에 필요하지 않다.
- `service_role`, 비밀번호, API 키와 실제 계정 정보는 저장소에 추가하지 않는다.
- 의존성 빌드 스크립트는 검토된 패키지만 허용한다.
- 별도 프로젝트의 소스와 환경 파일을 홈페이지 검사 결과나 커밋에 포함하지 않는다.
- 외부 네트워크 없이 실행 가능한 테스트는 네트워크 요청을 만들지 않는다.

## 9. 테스트 전략

### 9.1 자동 검사

- 기존 Node 테스트 255개 통과
- 홈페이지 범위 TypeScript 검사 통과
- ESLint 검사 통과
- Next.js 운영 빌드 통과
- 통합 `check` 명령 통과
- 설치와 검증 후 추적 파일의 예상하지 않은 변경 없음
- `ChatBot/`과 `Text-Play/`가 존재해도 홈페이지 검사 결과 동일

### 9.2 설정 회귀 검사

설정 파일을 읽는 작은 Node 테스트를 추가해 다음 계약을 검사한다.

- 별도 프로젝트가 Git과 TypeScript 검사 범위에서 제외됨
- 공식 검증 스크립트가 모두 존재함
- pnpm 설정이 작업 공간 설정에 존재함
- 필수 문서에 동일한 검증 순서가 기록됨

### 9.3 수동 확인

- 새 터미널에서 설치와 `check` 실행
- 개발 서버 실행 후 메인 페이지 접근
- 개발 서버 종료 후 Git 상태 확인
- 운영 빌드 후 Git 상태 확인

## 10. 완료 기준

1단계는 다음 조건을 모두 만족할 때 완료한다.

- 새 환경에서 `pnpm install --frozen-lockfile` 성공
- `pnpm check` 한 번으로 전체 검증 성공
- 기존 테스트 255개 이상 통과
- TypeScript, ESLint와 Next.js 빌드 성공
- 별도 프로젝트가 홈페이지 검사와 Git 상태에 영향을 주지 않음
- 개발 서버와 빌드 실행 뒤 추적 파일 변경 없음
- 외부 계정과 비밀 키 없이 검증 가능
- 개발 문서와 실제 명령이 일치함
- 방문자 화면과 기존 기능 동작에 변경 없음

## 11. 후속 단계와 연결

1단계 완료 뒤 2단계에서 프로젝트, 뉴스와 상품의 통합 콘텐츠 계약을 설계한다. 2단계는 로컬 데이터 공급자와 외부 공급자 인터페이스를 분리하고, 시연 정보가 실제 정보처럼 표시되지 않도록 콘텐츠 상태를 구조화한다.

1단계에서 추가하는 검증 명령과 저장소 경계는 이후 모든 단계의 공통 완료 조건으로 사용한다.
